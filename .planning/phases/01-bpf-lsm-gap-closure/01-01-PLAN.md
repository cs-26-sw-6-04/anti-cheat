  <read_first>

  <decision>
Which process is the "attacker" the inject enforcer (lsm/mmap_file) should block?

The lsm/mmap_file hook fires in the context of whichever process calls mmap(). A process
can ONLY mmap into its own address space -- there is no way for an external process to
directly mmap into another process's address space (that path goes via ptrace, which is
already blocked by AC_ENF_MEMORY).

Therefore, "blocking external PROT_EXEC mappings targeting the protected subtree" must mean
one of these interpretations:
  </decision>

  <context>
Research finding (RESEARCH.md A1): `lsm/mmap_file` fires when the calling process maps
memory. An external attacker cannot map into the game's address space directly -- ptrace is
needed for that and it is already blocked. The "inject" threat vector is therefore:
the game process (or a descendant inside the subtree) mapping executable code into itself
from an anonymous buffer (shellcode).

  </context>

  <options>
    <option id="option-a">
      <name>Fire when the protected process maps anonymous PROT_EXEC (interpretation a)</name>
      <pros>
        - Only direct route not covered by ptrace_access_check
        - Clear victim domain: caller IS in the protected subtree
        - Privacy-preserving: no path or file name logged
        - Testable with simple mmap(NULL, 4096, PROT_READ|PROT_EXEC, MAP_ANONYMOUS|MAP_PRIVATE, -1, 0)
      </pros>
      <cons>
        IMPORTANT CAVEAT: This also blocks JIT-compiled code. Every JIT runtime
        (V8/JavaScript, Mono/Unity C#, JVM, LuaJIT, Wine's Windows DLL loader)
        allocates anonymous PROT_EXEC pages at runtime. If the protected game
        uses any of these, this interpretation blocks legitimate operation.
        Only viable if the protected target is known to not use JIT.
      </cons>
    </option>
    <option id="option-b">
      <name>Skip inject enforcer entirely -- ptrace_access_check already covers external injection</name>
      <pros>No false positives; no JIT risk; REQ-01 is satisfied by documenting the coverage</pros>
      <cons>The mmap_file hook is not used; some /proc paths may still be uncovered (see A3)</cons>
    </option>
    <option id="option-c">
      <name>Fire when the protected process maps PROT_EXEC from a file-backed mapping of an unknown path</name>
      <pros>Targets shared library injection via unexpected paths</pros>
      <cons>Requires path inspection in BPF (complex, possible privacy violation), harder to test</cons>
    </option>
  </options>

  <decision>
Two related decisions needed for the execve enforcer:

DECISION A2: Which processes should the execve enforcer (lsm/bprm_check_security) block?

`ac_spawn_and_protect` attaches BPF BEFORE releasing the child via the barrier pipe.
The child's first action is to exec the game binary. If the enforcer blocks ALL execs from
the protected subtree, it blocks game startup itself.

DECISION A6: How should inject/execve tests exercise attacks from inside the protected process?

The existing `run_scenario` harness forks an EXTERNAL attacker. For inject (anonymous PROT_EXEC
mmap) and execve (exec from inside subtree), the attack must originate from INSIDE the protected
subtree -- the caller must be a member of the protected subtree for the enforcer to fire.
  </decision>

  <context>
A2 options:
  - (a) Fire only on exec from DESCENDANTS of ac_protected_root_pid, not the root itself.
        Root's exec is its startup; descendants should not exec without permission.
        Filtering: `me != ac_protected_root_pid` before the subtree check.
  - (b) Use a one-shot rodata flag allowing the first exec from root (contradicts GOALS.md
        "no central toggle" -- rejected unless user specifically requests it).
  - (c) Restructure ac_spawn_and_protect to attach AFTER the child execs. Introduces a
        window before enforcement (arch regression).
  - (d) Only fire on exec of files not backed by a filesystem entry (memfd/anonymous exec).

A6 options:
  - (b) New target factories (mmap_exec_self, exec_child): the target_fn itself performs
        the malicious action inside the protected process. The test has two sections:
        "attack succeeds" spawns without session; "protected" spawns with session.
        No changes to run_scenario harness needed.
  - (a) Extend run_scenario with a self_attack field (more complex, requires protocol change).
  </context>

  <options>
    <option id="a2-option-a-a6-option-b">
      <name>A2: descendants-only; A6: new target factories (recommended)</name>
      <pros>
        - A2(a): consistent with GOALS.md "no toggle"; root exec is startup; clean semantics
        - A6(b): minimal change to test infrastructure; factory pattern already understood
      </pros>
      <cons>
        - A2(a): a malicious process that replaces itself via exec at the root level is not caught
          (but this is an unusual self-replacement attack; root-level exec IS the startup)
        - A6(b): "attack succeeds" section must use a factory that internally mmap/execs and
          verifies the syscall succeeded, not an external run_attacker
      </cons>
    </option>
    <option id="a2-option-d">
      <name>A2: only fire on memfd/anonymous exec (fileless execution)</name>
      <pros>Allows all legitimate filesystem execs; catches the specific fileless attack vector</pros>
      <cons>
        Requires checking bprm->file's inode flags in BPF (complex CO-RE path);
        fileless exec is rarer and may not be the primary threat in the report
      </cons>
    </option>
    <option id="a2-skip">
      <name>Skip execve enforcer -- document as out of scope for this architecture</name>
      <pros>No first-exec complexity; no JIT risk</pros>
      <cons>REQ-02 is not delivered; report gap closure is incomplete</cons>
    </option>
  </options>
